# Архитектура комплекта ППО ВОЛС

Файл для той версии меня, которая откроет репозиторий в новой сессии. Здесь то,
что нельзя вывести из кода за разумное время: почему сделано так, где контракты
между частями и какие места уже ломались.

## Карта файлов

| Файл | Что в нём |

| `ppo-refs.js` | Пользовательский слой справочников: записи, добавленные вручную. Дописывается в массивы ядра при загрузке |

## Модель данных

Один объект обследования в `localStorage` под ключом `ppo_vols_object_v2`:

```
{ v, saved, pass:{}, lines:[], poles:[], meas:[], si:[], cables:[], wires:[],
  acts:[], skips:[] }
```

Фотографии — отдельно (IndexedDB), метки карты — отдельно, пользовательские
справочники — отдельно (`ppo_refs_user_v1`). Резервная копия `.json` собирает
всё вместе.

Ключевые поля опоры, появившиеся при доработках:

| Поле | Смысл |
|---|---|
| `endPole` | Конец участка: пролёта до следующей нет, цепь обрывается |
| `nextId` / `prevId` | Ручная привязка соседа по идентификатору опоры |
| `nextRef` / `prevRef` | Та же связь текстом «линия\|номер» — переживает круг через книгу |
| `spanGeo`, `spanNext`, `spanFlag` | Производные: расстояние по координатам, номер следующей, признак звена |
| `defText` | Описание. При категории «—» дефектом не считается |

Номер опоры **не уникален**: одноимённые опоры с разными координатами
допускаются. Однозначен только `id`. Все сопоставления идут в порядке
«идентификатор → пара линия+номер → координаты».

## Цепочка расчётов

```
координаты опор
   ↓ orderByRoute()        ход линии по геометрии (двухпроходный поиск края)
   ↓ splitChain()          разрыв на участки, отводы
   ↓ recalcSpans()         пролёты, spanGeo, признаки; ручные связи перекрывают ход
   ↓ chainSpans()          смежные опоры, расчётный (ветровой) пролёт lw
   ↓ objectLength()        протяжённость; syncObjectLength() пишет в паспорт
   ↓ assessAll() (index)   приложение Ж: моменты, запас
```

`poleChain()` кэширует результат до ближайшей записи объекта: за одно действие
на карте цепь запрашивалась пять-шесть раз, и это подвешивало браузер.
Обесценивание — по счётчику `_rev`, который поднимает `save()`.

## Контракт с книгой

Три пути записи, и это главный источник пропущенных правок:

| Путь | Когда | Что делает |
|---|---|---|
| `buildWorkbook()` | «Загрузить шаблон Excel», сборка отчёта значениями | Собирает книгу с нуля |
| `planFor(wbRead)` + `PPOXLSX.patch` | Заполнение скачанного шаблона | План точечных правок, сохраняет оформление |
| `fillTemplate(wb)` | Заполнение шаблона в памяти | Пишет в ячейки открытой книги |

Любая правка состава данных нужна во всех трёх. Проверяется сличением в
`tools/test-core.js`.

Чтение обратно — `importWorkbook(wb)`, **по именам заголовков**. Служебная графа
листа «Опоры» несёт машинные признаки:

```
КОНЕЧНАЯ                  конец участка
СЛЕД=линия|номер          следующая опора задана вручную
ПРЕД=линия|номер          предыдущая опора задана вручную
```

Формат разбирает `svcParse`, собирает `svcMark`.

## Шаблон `ID_shablon.xlsx`

Правится только скриптом `tools/build_template.py`, который пересобирает листы
справочников на уровне XML. Причина: в книге 21 проверка ввода, семь наборов
примечаний и своё оформление; пересохранение библиотекой их теряет.

Связанный список марок опор устроен так: на листе «Опоры» графа «Марка» имеет
проверку `=INDIRECT(IFERROR(VLOOKUP($D2,'Спр_Опоры'!$M$4:$N$12,2,0),"Опоры_10"))`,
где `M:N` — таблица «класс → имя диапазона», а диапазоны `Опоры_0_4`, `Опоры_6`,
`Опоры_10`, `Опоры_35`, `Опоры_110` объявлены в книге. Меняя состав марок, надо
пересчитать границы диапазонов — скрипт делает это сам.

Блок 2 листа «Нагрузки» берёт марки из именованного диапазона
`Подвеска_Марки` — сводного перечня «кабели + провода» на листе «Спр_Провода».

## Раскраска меток карты

Порядок важнее оттенка:

| Цвет | Значение |
|---|---|
| красный | дефект |
| жёлтый | не определён предыдущий либо следующий сосед по цепи |
| чёрный | фотографий нет |
| синий | фотографии есть |

Жёлтый совпадает с подсветкой карточки опоры в «Осмотре» — это одно и то же
состояние, показанное с двух сторон.

## Лист внутреннего контроля

Шесть разделов: комплектность, непротиворечивость, метрология, сроки, несущая
способность, разделение ответственности. Около шестидесяти проверок, статусы
«соответствует / внимание / несоответствие». Отчёт с несоответствиями
выпускается только под письменное обоснование ответственного лица, которое
печатается в самом листе.

Часть проверок живёт в `index.html` (`runAudit`), часть — в `ppo-audit.js`.
Модуль подключается отдельным тегом; если его нет в репозитории, отчёт честно
пишет «контроль выполнен в неполном объёме» — так однажды и было, вместе с
потерей сверки пролётов с координатами.

## Нормативная опора расчётов

ПП РФ № 2106 (состав отчёта, сроки), ПУЭ-7 (габариты, расстояния,
районирование), СП 20.13330.2016 (ветровые и гололёдные нагрузки, коэффициенты
типа местности), ФЗ № 102-ФЗ и приказ Минпромторга № 2510 (средства измерений,
ФГИС «Аршин»), ПП РФ № 160 (охранные зоны), ПП РФ № 87 (граница с проектной
документацией), приказ Минтруда № 903н (охрана труда), ГОСТ 31937-2024
(обследование), ГОСТ 22690-2015 (прочность бетона).

Коэффициент типа местности берётся по **первой букве** подписи поля: в поле
хранится полная формулировка, и поиск по всей строке однажды молча откатывался
к типу В, занижая ветровую нагрузку на 35 %.
